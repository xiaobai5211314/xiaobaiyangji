## CORS 跨域修复（guzhicdn 打不开，持仓转圈）

- **现象**：`https://guzhi.21212121.xyz`（源站同源）能打开，`https://guzhicdn.21212121.xyz`（CDN 跨域）持仓一直转圈。
- **根因**：`Program.cs` 缺少显式 `app.UseRouting()`。.NET 8 minimal hosting 会在 `MapControllers` 时隐式加 routing，导致 `app.UseCors("ConfiguredOrigins")` 实际跑在 routing **之前**。CORS 中间件无法匹配 endpoint，跨域 preflight（OPTIONS）不被拦截 → 路由层返回 **405**；响应也不加 `Access-Control-Allow-Origin` 头。guzhi 同源不需要 CORS 所以正常，guzhicdn 跨域全挂。
- **诊断证据**：Playwright 从 guzhicdn origin 发请求，带 Authorization 的 preflight 返回 405，响应头无任何 CORS 头。配置文件 `appsettings.Production.json` 和 systemd service 都正确（含 guzhicdn、ASPNETCORE_ENVIRONMENT=Production），nginx 反代也未剥离头。
- **修复**：`Program.cs` 第 140 行前加 `app.UseRouting();`，确保顺序 `UseRouting → UseCors → ... → MapControllers`。commit `f679f5a`，已部署（deploy-backend 1m5s success）。
- **验证**：部署后 Playwright 重测，带 Auth header 的请求从 405 → 200；browser_network_request 查看原始响应头确认含 `access-control-allow-origin: https://guzhicdn.21212121.xyz` 和 `vary: Accept-Encoding, Origin`。注意：fetch API 的 `res.headers.get('access-control-allow-origin')` 返回 null 是浏览器 CORS 响应头过滤，不代表后端没返回头——查 CORS 头必须用 network 层。
- **教训**：.NET 8 minimal hosting 下 `UseCors` 必须在显式 `UseRouting` 之后，否则 CORS 静默失效（不报错，但跨域全挂）。
